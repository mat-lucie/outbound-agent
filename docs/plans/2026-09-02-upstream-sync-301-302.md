## What was ported

### Upstream #301 — record manual LinkedIn DMs on Responded prospects

`workflows/detect_responses.py`: a new Phase 0.5 pass (`_detect_manual_touches`)
that re-uses the same inbox scrape the reply loop reads. For a `RESPONDED` entry
whose LAST message is ours, is not one of our DM templates, and carries a new
`sha1(totalMessageCount|body)` fingerprint, it stamps `last_contact_date` to the
row's `lastMessageDate` (never backwards; today only as a counted fallback),
files the body as a `DM manual — <date>` note, and persists the fingerprint in
`exports/manual_touch_state.json` (atomic temp+fsync+rename write, saved in a
`finally` so a mid-pass crash keeps the fingerprints of stamps that already
landed).

Fail-open by design: state-file, note and stamp failures are counted and logged
and never break Phase 0.5, whose `reply_detection_status` gates DM sends; only a
writer-registry violation halts. Guards ported in full — the pass skips the
whole run when the self-echo template matcher is offline (failing open there
would record our own template sends as manual touches and persist that), a name
matching several different people at `RESPONDED` is skipped loudly,
`merged_into` soft-deleted entries are ignored, and an unrecognized
`isLastMessageFromMe` value is inert rather than read as "the prospect wrote
last". Ten `manual_touch_*` counters are declared in `_empty_counts` and every
non-zero one is printed at the end of the phase.

`clients/attio_writer_registry.py`: `workflows.detect_responses._detect_manual_touches`
registered as a `("linkedin_outreach", "last_contact_date")` writer.

### Upstream #302 — cold-responder lane with paste-ready manual DMs

`models/followup.py`: `WarmLane.COLD_RESPONDER`, `FollowupReason.RESPONDED_COLD`,
and its policy — heat 4, **7 calendar days** (the WAITING floor, because this is
post-send silence on OUR message and a day-3 DM nudge reads as pressure).

`workflows/detect_responses.py` (scope A extension, additive): state entries
carry `ball: "ours"` + `last_body` (≤500 chars), and a scrape showing the
prospect's message last flips an EXISTING entry to `ball: "theirs"` +
`ball_observed` — local state only, no CRM write, no new entries.

`workflows/followup_radar.py`: the lane itself. `_read_manual_touch_state`
(read-only, never raises; corrupt → lane OFF + a degraded reason),
`_thread_direction` (the ONLY "ours last" evidence — the CRM rule
`last_contact_date > response_received_at` was tried and rejected upstream
because drift repair, the dedup MAX-merge and the consistency sweep all bump
`last_contact_date` on Responded entries with no message from us), promotion in
the entry loop with `email_responded` rows never promoted, a `ball: "theirs"`
entry keeping the row on the plain nudge path while contributing its reply as
the real last touch plus a "you owe a reply" note, the `their_last_reply` /
`our_last_dm` / `dm_language` candidate fields, `render_manual_dm`,
`_normalize_dm_language` (person `people.language` override > entry attr, via
`coerce_language`), the `cold_responder` partition bucket (own section — never
swallowed by LinkedIn-warm), the digest section with the exchange lines and the
DM as a blockquote, the generalized `_trim_with_lane_caps` (3-slot cold cap
alongside the 2-slot WAITING cap) and the summary/footer counts.

`cli.py`: the `cold responder` lane count in the radar footer, wording matched
to `render_digest` exactly.

Also ported: `render_digest` now renders EVERY note on a row (it previously
rendered `notes[0]` only, which would have buried the "you owe a reply" line
behind a stale-draft note), and `to_json` gains `notes`.

### Upstream #304 (one-line test-fixture fix)

`tests/test_integration.py` `_attio_with_full_schema` now sets
`attio._person_to_company = {}`: a bare `MagicMock` answers `.get()` with the
same child mock for every record, so every prospect looked like it shared one
company and the within-run same-company dedup silently dropped rows. The fork's
suite stays green with it.

## Fork adaptation seams applied

- **No `operator_id` / foreign-owner filter.** Upstream's `_filter_owned_entries`
  refactor (and the `operator_id=` parameter on the pass) belongs to a
  `prospect_ownership` feature this fork does not have — `detect_responses` here
  takes no operator id and no entry carries `owner`. Ported without it; upstream's
  two owner-filter tests were dropped rather than faked. Same call as sync 3's
  skip of `verify_email_send_preconditions`.
- **The DM copy is operator content, not engine code.** Upstream keeps the three
  DM templates in Python because putting them in `messages.json` would make the
  self-echo matcher classify a pasted DM as one of our own template sends. This
  fork honors that constraint *and* CONTRIBUTING's "engine code stays
  operator-neutral" rule by putting them in a SEPARATE content file,
  `content/followup_dm.json`, loaded via `models.campaign.load_followup_dm_templates`
  (so it follows `OUTBOUND_CONTENT_DIR` like every other content file) and never
  read by `load_messages()`. Repo-root ships neutral `REPLACE_THIS_TEMPLATE`
  placeholder copy; `examples/acme/content/followup_dm.json` carries the worked
  synthetic-Acme copy the suite asserts against. A missing/corrupt file or an
  absent language degrades to a visibly-broken placeholder (warn-once to stderr)
  rather than a generic bot line someone might paste — rendering happens inside
  the digest, which must never raise.
  The `{when}` silence phrases and their bucket bounds stay in code: the bounds
  are engine policy and the phrases are plain time vocabulary for the three
  languages the engine already supports.
- **Digest chrome is English.** Upstream's Spanish section title and row labels
  become "Cold responders — replied, then went quiet (paste by hand)",
  `them (date)` / `you (date)`, and `paste-ready DM (ES)`, matching the fork's
  existing English markers (`replied by email — no auto-draft`, `reply seen`).
  The rendered DM itself is of course in the prospect's language.
- **Language-unknown warning** is English (`[language not on record - defaulting
  to ES, check before pasting]`) for the same reason.
- Comments were rewritten in operator-neutral terms ("the operator", "the CRM")
  and carry no tracker ids or private-repo paths. No new `§N.N` / `PR-NN`
  provenance markers were invented (AGENTS.md).

## Known limits carried over from upstream

- Only the LAST message body per thread is visible to the scraper, so manual
  messages sent between two scrapes are lost.
- The state file is per-checkout: a run from a different checkout may re-note a
  touch once (dates are unaffected — the stamp is idempotent by value).
- The pass only runs when Phase 0.5 reaches the scrape; on a day with zero
  DM-stage prospects the early return skips it silently.
- The paste-ready name is the first whitespace-separated token of the CRM name,
  so a compound first name needs a manual touch-up before pasting.
